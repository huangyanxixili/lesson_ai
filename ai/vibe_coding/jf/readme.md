## Vibe coding 阶段
- 第一个阶段 prompt 
     一两句话描述需求，如果不满意再重新做
- 第二个阶段 设计prompt（prompt工程）
   - 给予一个角色   eg：你是一名高级前端开发工程师
   - 项目结构      eg：生成文件放置的位置
   - 代码规范      eg：全面使用 es6 + tailwindcss 语法
   - 现在需求是    eg：用户需求是实现一个简单的登录页面
   - 提供一个上下文
   - 要求输出格式   
     相比于第一阶段，提示词变得更专业，结构化了
     形成了一定的系统方法论、任务的拆解、用专业的术语去引导LLM
     能精准的控制氛围编程生成的内容
- 第三个阶段 多Agent（Agentci AI模式：代理式AI）
   - 在vibe coding 之前，先让 AI 生成**需求文档**（虚拟产品经理）
   - 再让 AI 根据需求文档 生成**设计稿**（虚拟设计师）
   - 最后让 AI 生成**前端代码**（虚拟前端开发工程师）
      懂规矩、更专业，按流程，可执行
    **生产级别的 vibe coding 标准做法**
- Spec-Driven Development（SDD） 规范驱动开发
    先写清楚详细的规格说明书（Spec），再让代码去实现这个规格

## 小结：
    第一阶段：代码几乎不能用，到最后大概率需要整体修改，反而浪费时间
    第二阶段：好很多，但是不能完全依赖它，仍然需要人工审核、调试
    第三阶段：直接落地，生产级别的vibe coding

    AI 编程 = 提示词 + AI 编程工具 + AI 大模型 + SDD

## SDD
Spec-Driven Development（规范驱动开发），简单说就是：先把“规则说明书”写清楚，再按说明书写代码。这里的“Spec”可以是接口文档、需求说明、行为描述，甚至是测试用例。

和“先写代码再补文档”不同，Spec-Driven 强调代码必须严格满足规范，而不是靠口头理解或临时改。这样做的好处是：需求更清晰、沟通成本更低、返工更少，也更容易做自动化测试。

举个例子：
你要开发一个“登录接口”。在写代码前，先写 Spec：
```md
接口：POST /login
入参：username、password
成功返回：{ code: 0, token }
失败返回：{ code: 401, message }
```
然后你再写后端代码、前端调用、测试用例，所有人都以这份 Spec 为准。如果代码跑不通，就说明不符合 Spec，而不是“理解不一致”。

一句话总结：Spec 是合同，代码是履约结果。
