### ACID
ACID 是描述**关系型数据库事务**行为的四个关键特性，用来保证在各种出错情况下（宕机、并发冲突、异常回滚）数据仍然**正确、可靠**。

事务（transaction）：数据库操作的最小单位
ACID = Atomicity + Consistency + Isolation + Durability

1. A：原子性（Atomicity）
一句话：**要么全成功，要么全失败回滚**

- 一个事务里通常包含多步操作：
  - 例如：A 给 B 转账 100 元：
    1. 从 A 账户扣 100  type = out
    2. 给 B 账户加 100  type = in
- 原子性保证：
  - 如果中途任何一步失败（比如程序异常等），整个事务会 **回滚** 到开始前的状态。
  - 不会出现“钱从 A 扣了，但没到 B”这种半成品状态。
打包里的所有 SQL 要么一起成功，要么全部不算。

2. C：一致性（Consistency）
一句话：**事务前后，数据必须从一个“一致状态”变到另一个“一致状态”**

- “一致状态”指的是满足所有约束：
  - 主键唯一
  - 外键约束
  - 不允许余额为负数
  - 业务规则（如转账后，A和B的总金额不变）
- 一致性保证：
  - 即使事务失败回滚后，数据库也不会变成乱七八糟的状态（比如约束被破坏）。
  - 任何时刻，数据库中存的数据都满足所有定义好的规则。
原子性更偏“操作是否全部执行”，一致性更偏“执行之后状态是否仍然正确”。

3. I：隔离性（Isolation）
一句话：**并发执行的事务之间，相互独立、互不干扰**

- 多个事务同时跑时，如果不做隔离，就可能相互干扰，导致：
  - 脏读（读到对方还没提交就回滚的数据）
  - 不可重复读（前后两次查到同一条记录却不一样）
  - 幻读（同一条件查询，两次结果集数量不一样）
- 隔离性保证：
  - 每个事务不会被其他事务正在进行中的修改搞乱。
- 实际上存在多个隔离级别（从弱到强）：
  - Read Uncommitted（几乎不用）
  - Read Committed
  - Repeatable Read（MySQL InnoDB 默认）
  - Serializable（最严格，几乎串行执行）
隔离性的本质是 **在“性能”和“并发安全”之间做平衡**：级别越高，越安全，也越可能影响性能。

4. D：持久性（Durability）
一句话：**事务一旦提交，结果就是“写死”的，即使断电重启也不会丢。**

- 当你执行 `COMMIT` 后，数据库承诺：
  - 已提交的数据会被可靠地写入持久存储（磁盘、日志等）。
  - 即使服务器重启，事务提交后的数据依然存在，不会退回到之前的状态。
- 实现手段：
  - 写 WAL（Write-Ahead Log，重做日志）。
  - 崩溃恢复时，通过日志重放，把已提交但未完全写入的数据补写回去。
持久性保证的是“提交成功后，结果不可凭空消失”，对应的是“不会丢帐”。

你是一位psql高级工程师，需要设计一个user表，

```sql
CREATE TABLE users (
    -- 使用 BIGINT 避免未来数据量过大导致 ID 溢出，IDENTITY 是 SQL 标准自增方式
    -- INT（上限21亿) BIGINT（8字节）
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    
    -- UNIQUE 约束会自动创建索引，NOT NULL 保证数据完整性
    name VARCHAR(255) NOT NULL UNIQUE,
    
    -- 密码字段，通常长度设为 255 以适配各种哈希加密算法（如 bcrypt）
    password VARCHAR(255) NOT NULL,
    
    -- 高级工程师通常会增加这两个审计字段
    created_at TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP
);
```

prompt：
 你是一位psql 高级工程师， 需要建一个posts 表， 包含id, title, content,userId 三个字段。id 自增， 主键， title 不为空，不超过255个字符， content  长文本，  usersId 是bigint 类型，是 users 表的外键，请给出建表sql

```sql
CREATE TABLE posts (
    -- 1. ID: 使用 BIGINT 配合 IDENTITY 标准，优于旧式的 SERIAL
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,

    -- 2. Title: 限制 255 字符，非空
    title VARCHAR(255) NOT NULL,

    -- 3. Content: 使用 TEXT 存储长文本
    -- 在 PG 中，TEXT 和 VARCHAR(n) 性能几乎一致，TEXT 更适合长文
    content TEXT,

    -- 4. UserID: 外键字段
    -- 建议设置为 NOT NULL，除非允许"匿名"帖子
    "userId" BIGINT NOT NULL,

    -- 5. 审计字段 (高级工程师通常建议加上这两个字段)
    created_at TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP,

    -- 6. 外键约束
    -- ON DELETE CASCADE 意味着如果用户被删除，该用户的帖子也会自动被删除
    CONSTRAINT fk_user
        FOREIGN KEY ("userId")
        REFERENCES users(id)
        ON DELETE CASCADE
);

-- 7. 性能优化：为外键创建索引
-- PostgreSQL 不会自动为外键创建索引，为了查询性能（如查询某用户的所有文章），必须手动创建
CREATE INDEX idx_posts_user_id ON posts(user_id);
```

### http 请求动作
**语义化** **restful 一切皆资源**
Method + URL 定义方式
1. GET --- 获取（查）  
  获取资源，不能修改服务器数据
2. POST --- 新增 / 提交（增）
  向服务器提交数据，通常用于创建新资源
3. PUT --- 整体更新（改）
  用请求体中的完整资源“替换”服务器上的资源，例如：上传（更新）头像
4. PATCH --- 局部更新（改）
  对资源进行部分修改（不像 PUT 那样整体替换）
5. DELETE --- 删除（删）
  删除资源
